Ideia central

Uma pageview não é uma request no CMS. É de 2 a 15 requests — o multiplicador vem da configuração da página (nº de blocos dinâmicos, filtros, relações), não do visitante. Por isso o volume no CMS pode subir sem o tráfego subir: basta um editor adicionar um bloco.

O que faz o volume subir sem tráfego humano subir
  • Editor adiciona 1 bloco dinâmico numa página vista por 100k pessoas/dia → +100k requests/dia no CMS.
  • Editor liga filtros num bloco → dobra o custo daquele bloco em toda pageview.
  • Bot novo crawlando o sitemap → mesmo fan-out de humano, sem short-circuit.
  • Monitor externo hitando `/` a cada minuto → sem cache, cada hit paga o preço cheio.

2. O que o Hosting faz (e o que não faz)

Achado importante: o hosting-api não é intermediário em runtime. Isso descarta ele como amplificador do volume no CMS.

  • Publicação: hosting-api → cms-api = 1 request (criar/reusar API key do canal).
  • Runtime: renderer → hosting-api = 0 requests (renderer lê S3 direto).
  • Runtime: renderer → cms-api = onde tudo acontece.

Conclusão: volume no CMS depende de quantas páginas são vistas × quantos blocos dinâmicos cada página tem, e não de quantas publicações ou uploads acontecem.

Esta é a resposta central para "por que o volume sobe sem o tráfego subir".

O ponto de dor

Os fatores marcados como "Sim — cada visita paga" são a raiz do problema: adicionar 1 bloco dinâmico é uma decisão single-click no builder que aumenta o volume no CMS na proporção do tráfego daquela página. Um editor pode dobrar o custo em OpenSearch sem escrever uma linha de código, sem revisão de PR.

O que os dados reais de prod mostram

Das 13.241 páginas com estrutura no hosting, 4.545 (34%) não têm bloco dinâmico algum. As 8.696 restantes (66%) concentram todo o volume, com média de 2,44 blocos por página. A cauda vai até 13 blocos numa única página. O bloco mais usado (DynamicCarouselAndGrid) aparece 8.177 vezes em 4.799 páginas — média de 1,70× por página, ou seja, muita duplicação. Ver dashboard completo.

4. Por que blocos idênticos duplicam?

A pergunta que aparece quando você olha o fluxo: se dois blocos na mesma página pedem exatamente o mesmo conteúdo, o renderer manda uma request só ou duas? Manda duas. E se pedem para o mesmo content type com filtros diferentes? Duas. Não existe deduplicação em nenhuma camada.

A regra dura

Cada bloco dinâmico na página vira uma request HTTP independente ao cms-api, sempre. O renderer não checa se dois blocos têm URL idêntica antes de disparar. O cms-api não tem endpoint de batch. Cada request refaz todo o trabalho: valida API key no Postgres, resolve o ContentType no OpenSearch, busca entries, resolve relações.

Como o código está estruturado

O orquestrador é fetchAllDynamicContents em packages/blocks/src/utils/cms.ts. O que ele faz, em resumo:

1. Lê a árvore da página (Craft.js): { ROOT, nodeA, nodeB, nodeC, ... } 2. Filtra os nodes que têm contentTypeId 3. Para CADA node, monta uma promise INDEPENDENTE: const promises = cmsNodeIds.map(async (nodeId) => { const config = dynamicContents[nodeId]; // config do nodeId return Promise.all([ fetchCMSList({ contentTypeId, filters, order, max, ... }), hasAvailableFilters ? fetchCMSAvailableFilters({...}) : null, ]); }); 4. await Promise.all(promises) // todos os nodes em paralelo

A chave da resposta: o map é sobre nodeId, não sobre contentTypeId. Cada node vira uma promise, e nada compara "esse pediria a mesma coisa que aquele".

Quando duplica de verdade vs quando é só custo alto

Cenário Requests HTTP Dedup possível?
2 blocos, mesmo CT, filtros/order/max idênticos 2 idênticas Sim — 100% desperdício
2 blocos, mesmo CT, filtros diferentes 2 diferentes Não — respostas seriam diferentes
2 blocos, mesmo CT, mesmo filtro mas max diferente 2 Parcial — poderia buscar o maior e cortar
2 blocos, CTs diferentes 2 Não — nunca duplicáveis
5 blocos, todos com availableFilters ligado 10 (5×2) Parcial — filters do mesmo CT com mesmo escopo pode virar 1

Reforço: mesmo no primeiro caso (100% desperdício), o código atual dispara duas requests. Não existe hash de "URL + params" que evite isso.

Evidência de duplicação no parque real de prod

Contando ocorrências vs. páginas em que aparecem (medido em 2026-09-22):

  • MediaSectionDynamic: 2.029 ocorrências em 958 páginas → média 2,12× por página (o pior)
  • DynamicCarouselAndGrid: 8.177 em 4.799 páginas → média 1,70× (~3.400 requests extras)
  • UnitInfo: 191 em 118 páginas → média 1,62×
  • DynamicList: 4.207 em 3.823 páginas → 1,10× (384 duplicações)

Isso é a taxa observada em produção — cada duplicação é uma request extra ao CMS que a arquitetura não dedup. Tabela completa dos 15 tipos.

Por que ficou assim (as decisões que fazem sentido)

Não é ingenuidade — cada decisão isolada faz sentido. O problema é o efeito acumulado.

  • Blocos são configurações independentes. Cada bloco tem sua config (max, filtros, order, paginação, availableFilters, relações). Fazer merge automático arriscaria devolver dados errados.
  • Modelo mental do builder. Cada bloco é uma "vitrine" isolada que o racer configurou. Uma URL por bloco espelha exatamente a config — ajuda debug e log.
  • Promise.all esconde a latência. 5 requests paralelas custam quase o mesmo tempo que 1. O usuário não sente. Só o custo cumulativo do CMS aparece.
  • CMS público é REST simples, sem batch. O contrato é 1 request → 1 lista. Não existe POST /entries/batch. Adicionar é possível mas exige migrar chamadores.
  • Sem estado compartilhado entre blocos. Cada request é auto-contida. Bom para escalabilidade, mas impede "otimizar sabendo que 5 requests vêm da mesma pageview".
Insight cultural

A arquitetura atual é ótima para páginas com 1-3 blocos. Vira problema quando páginas complexas viram norma. Ninguém está impedindo o editor de colocar 5 blocos de "veículos" numa página. Nenhum guardrail no builder alerta ("você tem 3 blocos idênticos, deseja consolidar?"). Talvez o menor esforço de todos seja um lint no editor.

Análise arquitetural completa com as 5 alternativas de otimização (do cache in-memory ao GraphQL): docs/arquitetura-blocos-dinamicos-fanout.md.

6. O que acontece dentro do CMS por request

Cada request pública ao cms-api dispara múltiplas queries no OpenSearch e no Postgres. Este é o segundo estágio de amplificação — o que a métrica do Bonsai captura.

Pior caso real medido

O content type Modelo (o "hub" do catálogo automotivo) tem 29 campos + 5 relações → uma única request listPublicEntries desse tipo dispara 8 queries OpenSearch. O Versao de Veiculo tem 43 campos + 4 relações → 7 queries. Como esses dois são os "hubs" do domínio e vivem na conta compartilhada general (consumida por todas as ~143 contas do hosting), qualquer request para eles paga o preço máximo do fan-out.

Ausência total de caches no cms-api
  • Sem cache in-memory (não há LRU nem node-cache).
  • Sem Redis cache (Redis só serve BullMQ das filas).
  • Sem Cache-Control nos responses — CMS não instrui CDN a cachear.
  • Sem cache de API key — cada request bate no Postgres pra validar.
  • Sem cache de ContentType — cada request bate no OpenSearch pra resolver schema (que muda raríssimo).

Consequência: 100 visitantes olhando a mesma página no mesmo segundo geram 100× o mesmo trabalho. Nada é deduplicado.

Requests ao CMS por 1000 pageviews (por perfil de página)

Perfil A: sem blocos dinâmicos. B: home 1 bloco sem filtro. C: listagem com filtros. D: detalhe com 2 blocos. E: landing densa 5 blocos.

Queries no OpenSearch por 1000 pageviews

A quantidade multiplica por 2 a 4 quando comparada a requests, dependendo do fan-out interno do cms-api.

8. Ranking dos culpados

Ordenando por impacto esperado no volume total, baseado nas evidências:

  • #1
    Nº de blocos dinâmicos por página × filtros habilitados
    Multiplicador direto por pageview. Toda vez que alguém adiciona um bloco no builder, o site inteiro sente. Decisão editorial que ninguém revisa.
  • #2
    Ausência de deduplicação e cache em qualquer camada
    Blocos idênticos na mesma página não são deduplicados (ver seção 4). Não há CDN na frente do renderer, nem Cache-Control no CMS, nem cache in-memory do ContentType, nem cache da API key. Cem hits idênticos = cem trabalhos idênticos.
  • #3
    Página de detalhe multiplica por relações
    getPublicEntry com M relações requisitadas dispara M queries getContentTypeById extras. Coleções bem relacionadas amplificam.
  • #4
    Interações client-side (paginação, filtros na URL)
    Cada clique refaz caminho quase inteiro. Filtro na URL re-executa getServerSideProps. UX densa = volume alto.
  • #5
    Sitemap paginado
    Cache de 5min ajuda, mas cada expirada dispara ceil(entries/100) requests por coleção. Bots respeitam esse cache; monitores externos não.
  • #6
    Detalhes despercebidos
    siteId presente adiciona 1 OS query. getAvailableFilters sempre roda mesmo com filtros sem uso real. API key valida no Postgres a cada request.
  • #7
    Bots com crawl agressivo
    Não é o driver principal em condições normais, mas é o wildcard: crawler novo pode explodir volume em horas.

9. O que não aumenta volume no CMS

Para fechar a lista, o que não contribui (contra intuições comuns):

  • Publicar canais (hosting → CMS = 1 request por publish; irrelevante).
  • Editar metadata.json, header, footer, styleguide (S3 direto, sem CMS).
  • Uploads no S3, invalidação de CloudFront.
  • Leads/formulários (vão para crm-api/hosting-api, não CMS).
  • Assets estáticos (/_next/static/...) — servidos pelo CDN.
  • Tráfego cross-domain de outros canais — cada canal tem sua própria API key mas o padrão é idêntico; não há multiplicador surpresa.
