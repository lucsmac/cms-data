Diagnóstico principal

93% do volume OS vem de 2 operações de search (cms_content_types_v2 + cms_content_entries_v3), geradas por 100% pelos 3 endpoints públicos chamados pelo renderer no SSR de sites publicados. O fan-out de 2,01 queries OS por HTTP request é a assinatura de N+1 no lookup getContentTypeById.

⚠ Descoberta lateral: volume de pageviews desproporcional

O renderer faz 3.620 rpm em S3 para JSONs de páginas — extrapolando por ~6 fetches S3/pageview, dá ~600 pageviews/min ≈ 865K pageviews/dia. Se o volume esperado é ordens de grandeza menor (poucos sites × poucas visits/dia), há forte suspeita de tráfego não-humano (AI crawlers, uptime monitors, scanners). Confirmar via User-Agent está pendente — NR não captura headers por default.

Confirmação: renderer é a única fonte do CMS

511 rpm saindo do renderer para cmsv3.autodromo.com.br vs. 514 rpm chegando no cms-api nos endpoints públicos. Diferença de 0,6% (ruído estatístico). 100% do tráfego CMS vem do renderer — descarta qualquer suspeita de cliente externo, script, ou consumidor não-mapeado.

Alerta: latência do CMS ↔ renderer

Response time médio do renderer → CMS: 804 ms. Bonsai reporta 2-6ms de latência interna. Cada request CMS custa ~800ms do SSR — em páginas com múltiplos blocos dinâmicos em paralelo, chega aos 5,8s worst-case observados. Explica o Apdex de 71,69%.

9. Quick win: cache in-memory de getContentTypeById

Impacto quantificado

Métrica Antes Depois Redução
Queries OS/min 1.035 ~501 -51,6%
Queries OS/dia 1,49M ~721K -769K/dia
Total Bonsai/dia 1,6M ~830K -48%
Índice content_types_v2 534 c/min ~0 -100%
Bônus: latência do próprio cms-api

New Relic mostra 110ms de avg por query em content_types_v2, enquanto o Bonsai reporta 2ms median / 6ms p95 no cluster. Isso significa ~108ms de overhead por query fora do cluster (rede, TLS, connection pool, serialização). Cache local elimina esse overhead 100% — impacto direto em latência do SSR do renderer e no Apdex de 71,69%.

10. Anomalias e follow-ups fora do escopo

Investigações abertas
  • Origem do tráfego no renderer (bloqueada) — NR não captura User-Agent por default no agente Node. Habilitar attributes.include: ['request.headers.userAgent'] em apps/renderer/newrelic.js ou usar newrelic.addCustomAttribute no getServerSideProps. Alternativa: ALB access logs (se habilitados).
  • HEAD / = 3% do tempo — provável uptime monitor. Verificar quem bate e se Next roda SSR pra retornar só headers.
  • GET /404 = 2,52% do tempo — verificar se rota 404 dispara fetches ao S3/CMS antes de decidir que é 404. Se sim, esforço grátis pra evitar.
  • Highest error rate: 100% — algum endpoint falha 100% no período; descobrir qual
  • Slowest avg response: 5,8s — SSR trava em 5,8s no pior caso, provavelmente /entries/:slug com relações pesadas
  • Apdex 71,69% dissatisfying — reflexo do item anterior no experience real
  • msearch.create (1,31%) — o que é? Otimização legítima ou padrão a substituir?
  • Connection pool / keep-alive OS — 108ms de overhead sugere conexão não reusada; ver openSearchConfig.ts

11. Ações priorizadas

  • P1
    Cache in-memory de getContentTypeById
    TTL 5-10min + invalidação por mutação de ContentType/Field. Biblioteca: lru-cache (~20 linhas). Hit rate esperado >99% (content types são editados raríssimo).
    Impacto: -48% no Bonsai · Esforço: baixo
  • P1
    Habilitar captura de User-Agent no NR do renderer
    Sem isso, a origem dos ~865K pageviews/dia fica cega. Adicionar attributes.include: ['request.headers.userAgent', 'request.headers.host'] em apps/renderer/newrelic.js. Deploy leve, sem código.
    Impacto: desbloqueia investigação da causa raiz do volume · Esforço: mínimo
  • P2
    Cache HTTP + CDN para /available-filters
    Filtros mudam pouco; hit rate alto esperado.
    Impacto: -9 a -13% adicionais · Esforço: baixo
  • P2
    Cache-Control público em /entries + CDN
    TTL curto (30-60s) + CDN na frente absorve bots e re-visitas próximas.
    Impacto potencial: -20 a -30% adicionais · Esforço: baixo
  • P2
    CDN + Cache-Control no renderer
    Se confirmado que 865K pageviews/dia vem majoritariamente de bots/crawlers, um CDN na frente do renderer com TTL curto (mesmo 30s) reduz muito a carga tanto do renderer quanto do CMS. Depende de definir User-Agents que podem cachear e ver conteúdo estático.
    Impacto potencial: -50% ou mais · Esforço: médio
  • P3
    Short-circuit em HEAD / e GET /404
    Verificar se essas rotas ainda fazem fetches externos. Se sim, curto-circuito bare-metal antes do getServerSideProps economiza ~5,5% do tempo de I/O do renderer.
  • P3
    Investigar anomalias fora do escopo
    Transação com 100% error rate, SSR lento de 5,8s, keep-alive do cliente OS.

12. Conclusão

O volume de 1,6M requests/dia ao Bonsai não é um mistério: é o resultado direto de ~740K requests HTTP ao cms-api, com fan-out 2:1 confirmado. Metade dessas queries é evitável trivialmente com cache in-memory do lookup de content type.

Porém, apareceu um segundo problema: o renderer processa ~865K pageviews/dia — número que não bate com o volume esperado de clientes. Antes de assumir que é tráfego legítimo, precisa validar via User-Agent (bloqueado hoje por config default do NR). Se boa parte for bot/crawler, o real ganho não é otimizar OS — é colocar CDN na frente do renderer.

A spike do OS está concluída: caminho claro para -48% no Bonsai com uma mudança de baixo esforço. Uma investigação nova está aberta: descobrir de onde vêm os pageviews.
