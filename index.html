Como ler este documento

O objetivo é entender por que o Bonsai (OpenSearch) recebe 1,6M requests por dia. A investigação segue o caminho da chamada: começa no cluster (o que executa as queries), identifica quem gera cada query no cms-api, e sobe até a rota do renderer que originou o tráfego. Ao final, chega-se ao diagnóstico principal e às ações que podem reduzir o volume.

Diagnóstico principal: 93% do tráfego do OpenSearch vem de apenas 2 operações (busca em cms_content_types_v2 e cms_content_entries_v3). Elas são acionadas por 3 endpoints públicos do cms-api, chamados pelo renderer durante o SSR das páginas. A cada request HTTP que o cms-api recebe, ele faz 2 buscas no OpenSearch: uma para descobrir o tipo de conteúdo (getContentTypeById) e outra para o dado em si. Como o tipo de conteúdo muda raramente, essa primeira busca é evitável com cache.

Do lado da demanda: o tráfego é concentrado em poucas contas. Grupo Parvi + Grupo Automob juntos respondem por 62% dos requests e 76% do bandwidth do cms-api. Não é volume de bots — o padrão temporal é claramente humano/comercial (pico às 17h BRT, vale às 03h-06h BRT). Contas diferentes geram tráfego proporcional ao número de blocos dinâmicos por página dos seus sites — daí Geely Brasil ter muito pageview no renderer mas pouco impacto no CMS (site institucional, poucos blocos dinâmicos), enquanto Parvi tem menos pageviews mas cada uma dispara muitas chamadas ao CMS (dealers com listagens de veículos, filtros, relações).

Sobre a solidez dos números

Todos os dados abaixo vêm de medições independentes: New Relic APM do cms-api, New Relic APM do renderer, e o dashboard do Bonsai. Isso significa que estão sujeitos a sampling (o agente não coleta 100% dos eventos), instrumentação parcial (o agente do Node pode não capturar chamadas feitas via fetch nativo), e janelas de 24h possivelmente desalinhadas entre prints feitos em momentos diferentes.

Quando números de fontes diferentes parecem "casar", isso é consistente com uma hipótese, não uma prova dela. Trate cada correlação como forte indício até haver medição per-request.

⚠ Sinal crítico: o plano Bonsai está saturado — isso não é só sobre volume, é sobre fila

Dois gráficos do dashboard do Bonsai mudam o framing do problema:

  • Concurrency: linha topada em 2 durante toda a janela observada. Esse é o teto do plano atual — o cluster nunca consegue processar mais de 2 queries simultâneas. Quando chega uma 3ª, ela entra em fila.
  • Proxy Queue time: tempo acumulado de queries esperando slot livre. Cresce ao longo do dia e spike a ~800k ms por volta das 15:00 em 22/09. Esse tempo é somado direto à resposta de cada query, e por transitividade à latência do SSR do renderer que está esperando o cms-api.

Consequência prática: as 48% de queries evitáveis (lookup redundante de content type) não estão só ocupando volume — estão gastando slots de concorrência do teto, empurrando as queries que realmente precisam ir ao índice para a fila. Cortar essas queries libera slots, e o efeito na latência p95 tende a ser desproporcionalmente maior que os -48% de volume bruto, porque queue time cresce não-linearmente perto do teto.

Escalar o plano Bonsai para aumentar o teto é uma resposta ao sintoma, não à causa. Antes de pagar mais por concorrência maior, faz sentido parar de gastar slots com um lookup evitável.

Timeline por hora mostra vale às 03h-06h BRT (13-16K req/h) e pico às 17h BRT (50K req/h). Ratio pico/vale = 4×, clássico de tráfego real. Não é bot dominante — se fosse, a linha seria plana 24/7.

4c. Por que contas diferentes geram tráfego diferente — fan-out per site

Um insight importante: tráfego no renderer não é igual a tráfego no cms-api. Um site com muitos pageviews mas poucos blocos dinâmicos gera pouco tráfego no CMS. Um site com poucos pageviews mas muitos blocos dinâmicos gera muito. Isso explica a discrepância entre o ranking do renderer (onde Geely Brasil aparece com 34% das pageviews) e o ranking do cms-api (onde Geely Brasil é só 10%).

A conta que interessa

CMS requests por site ≈ pageviews × blocos dinâmicos médios por página × 1,14

O fator 1,14 vem de available-filters, chamado em paralelo com entries em blocos que têm filtros habilitados (~14% dos blocos, ver Seção 4b).

Queries para calcular fan-out per site

1. Requests do cms-api agrupados por siteId (empírico)

CloudWatch Logs Insights, /aws/ecs/mono-cms-prod-web:

fields @timestamp, message
| filter message like /GET \/content-entries\/public\/.*ms$/
| parse message /siteId=(?<siteId>[a-f0-9-]{36})/
| parse message / (?<status>\d+) (?<size>\d+) - (?<duration>[\d.]+) ms$/
| filter isPresent(siteId)
| stats count(*) as requests, sum(size)/1024/1024 as MB, avg(duration) as avgMs by siteId
| sort requests desc
| limit 50

FACET capture(http.url, r'amazonaws.com/(?<site>[^/]+)/styleguide')

Observação sobre HEAD e 404

Duas rotas chamam atenção pelo tempo consumido em I/O externo:

  • HEAD / = 3,00% (17,8k s) — o método HTTP HEAD é usado para verificar se uma URL responde sem baixar o corpo. Se o Next.js rodar getServerSideProps para HEAD (comportamento padrão em muitas versões), o handler faz todas as buscas ao S3 e CMS, mesmo que apenas os headers sejam retornados. Vale verificar no código se há short-circuit.
  • GET /404 = 2,52% (14,9k s) — páginas que não existem também estão consumindo tempo em I/O externo. Isso sugere que a rota _error/404 pode estar disparando getServerSideProps antes de decidir que não há página, buscando metadata e outros JSONs no S3 desnecessariamente.

Se qualquer uma dessas duas rotas puder retornar mais cedo (antes de fetches externos), o tempo economizado seria significativo — mas precisa ser verificado no código do renderer antes de agir.

8. Fan-out: quantas queries no OpenSearch cada HTTP request gera

Chegou a parte central do diagnóstico. "Fan-out" é a razão entre quantas queries um request HTTP gera no backend — no nosso caso, quantas queries OpenSearch cada request HTTP no cms-api dispara. Se cada request gera N queries e o volume HTTP é X, o volume OpenSearch é N × X. Isso permite entender se o problema é de volume de requests (muitos clientes) ou de amplificação por request (uma request gera muitas queries).

10. Aprofundamento em dois pontos abertos

Dois pontos ficaram sem explicação clara depois da primeira passada. Ambos foram investigados diretamente no código-fonte (via grep e leitura das rotas). Um deles ficou com hipótese refinada mas ainda sem prova; o outro ficou mapeado no comportamento mas com contribuição incerta ao volume final. É importante manter esses pontos visíveis para que decisões futuras não os ignorem.

Investigação 1 — Discrepância no /entries/:slug

Renderer /[slug]/[item] = 58,8 rpm · CMS /entries/:slug = 72,2 rpm · +13,4 rpm inexplicados (+23%)

O que o grep confirmou

  • Único caller de fetchCMS() em produção: pages/[slug]/[item].tsx:157
  • Chamado exatamente 1× por pageview, dentro de um Promise.all
  • Nenhum loop sobre relações, nenhum bloco dinâmico chama fetchCMS(), nenhuma API route chama
  • Único outro hit é em packages/blocks/src/utils/cms.test.ts (testes)
⚠ Falso positivo descartado

A tentação foi atribuir os +13 rpm ao fato de getPublicEntry no cms-api fazer 2-4 sub-queries internas (2× getContentEntryBySlug se tem siteStatusFilter, + resolveRelationLookup, + buildSiteStatusContext). Isso não explica — sub-queries dentro de um handler HTTP inflam span rpm (OS/Prisma), não a transaction rpm do endpoint. NR conta HTTP requests recebidos, não spans internos.

Candidatos remanescentes (sem evidência forte)

  • Sampling variance do NR — 23% em rpm dessa ordem pode estar no ruído do agente
  • Retries HTTP em erros de rede ou 5xx — 1 request no renderer vira 2 no cms-api
  • Janelas de 24h desalinhadas entre os prints (foram tirados em momentos diferentes)
  • HEAD /[slug]/[item] (~0,91 rpm no top 20) — insuficiente pra 13 rpm
  • Fetch nativo escapando da instrumentação NR em algum lugar
  • Alguma rota fora do top 20 chamando fetchCMS (não visível)

Status: inconclusivo Para resolver de vez, precisa instrumentar o cms-api com um header ou query param indicando a rota do renderer, ou fazer per-request join entre logs dos dois APM.

Investigação 2 — Contribuição do sitemap

Renderer /sitemap.xml = 1,73 rpm · /api/sitemap/[name] = 1,71 rpm · Total: 3,44 rpm

Como funciona

  • Gerado on-demand — pages/sitemap.xml.tsx não é pré-gerado nem cacheado em servidor
  • Cache-Control max-age=300, s-maxage=300, stale-while-revalidate=600 — CDN absorve 5min de tráfego
  • Ambas as rotas (/sitemap.xml e /api/sitemap/[name]) chamam collectSitemapUrls(host) completo — não compartilham dado in-process
  • fetchAllEntries pagina em loop com per_page: 100

11. Quick win: cache in-memory do getContentTypeById

Como o diagnóstico mostrou que o lookup de content type é responsável por praticamente metade das queries do OpenSearch, a otimização mais direta é evitar essa query quando ela é redundante. Content types mudam raramente (só quando alguém edita a estrutura de dados no builder), então guardar o resultado em memória por alguns minutos é seguro e resolve a maior parte do problema com uma mudança pequena.

Impacto quantificado

Métrica Antes Depois Redução
Queries OS/min 1.035 ~501 -51,6%
Queries OS/dia 1,49M ~721K -769K/dia
Total Bonsai/dia 1,6M ~830K -48%
Índice content_types_v2 534 c/min ~0 -100%
Bônus: latência do próprio cms-api

New Relic mostra 110ms de avg por query em content_types_v2, enquanto o Bonsai reporta 2ms median / 6ms p95 no cluster. Isso significa ~108ms de overhead por query fora do cluster (rede, TLS, connection pool, serialização). Cache local elimina esse overhead 100% — impacto direto em latência do SSR do renderer e no Apdex de 71,69%.

Bônus 2: alívio direto da fila do Bonsai

Como o plano atual tem concorrência topada em 2 e o Proxy Queue time já sobe durante o dia (spike observado de ~800k ms em 22/09 15:00), cada query eliminada libera um slot de concorrência para as queries que realmente precisam ir ao índice. O efeito na latência p95 tende a ser maior que os -48% de volume bruto, porque queue time cresce não-linearmente perto do teto — reduzir a demanda em 48% quando o sistema está saturado gera alívio proporcionalmente maior no tempo de espera.

Métrica a acompanhar pós-deploy: o pico de Proxy Queue time no dashboard do Bonsai deve cair drasticamente. Se não cair, a hipótese de que o gargalo é o lookup de content type está errada e vale reinvestigar antes de aumentar o plano.

12. Pontos observados fora do escopo direto

Ao longo da investigação apareceram sinais que não afetam diretamente o volume de requests no OpenSearch, mas merecem ser registrados para tratamento posterior. Cada um vale um card separado.

Lista para follow-up
  • Alguma transação com error rate de 100% — o overview do New Relic mostra um endpoint falhando em todas as requisições no período. Não sabemos qual — precisa filtrar no APM por transaction name para identificar.
  • Resposta mais lenta observada: 5,8 s — no pior caso, o SSR do renderer demora quase 6 segundos. Provavelmente ocorre em /[slug]/[item] quando o content type tem muitas relações a resolver, cada uma com seu próprio custo.
  • Apdex de 71,69% — o índice de satisfação do usuário está em zona "dissatisfying" no New Relic. É consequência direta da latência alta descrita acima.
  • Overhead de ~108 ms por query no cliente OpenSearch — o Bonsai processa cada query em 2-6 ms, mas o New Relic mede 110 ms de média. A diferença é rede + TLS + pool de conexões. Vale verificar em openSearchConfig.ts se o pool está configurado para reuso (keep-alive).
  • HEAD / e GET /404 consomem tempo de I/O externo — como mostrado na seção 7, essas rotas gastam ~5,5% do tempo do renderer em fetches ao S3 e CMS. Verificar se é possível short-circuitar essas rotas antes de getServerSideProps.
  • msearch.create (1,31% do tempo total) — operação do OpenSearch que faz múltiplas buscas em uma request. Vale confirmar se é uma otimização intencional (agrupamento de queries) ou padrão herdado que pode ser substituído.

13. Ações priorizadas

A ordem abaixo reflete impacto × esforço × confiança no dado. As ações P1 se baseiam em medição direta e têm baixo risco de execução. P2 depende de medição adicional para calibrar impacto real. P3 são melhorias que não afetam o problema principal, mas foram observadas no caminho.

  • P1
    Cache in-memory do getContentTypeById
    O maior consumidor do OpenSearch é o lookup de tipo de conteúdo, chamado 1× por request público. Como o tipo de conteúdo raramente muda, cachear em memória com TTL de 5-10 minutos (mais invalidação por evento em mutações de ContentType/Field) resolve. Implementação sugerida: biblioteca lru-cache, ~20 linhas no service.
    Impacto: -48% no Bonsai · Esforço: baixo · Confiança: alta
  • P2
    Instrumentar cms-api para atribuir requests à rota do renderer
    Adicionar um header custom (X-Renderer-Route) ou query param nas chamadas do renderer ao cms-api. Assim, o New Relic do cms-api consegue mostrar quantos requests em /entries vieram de /[slug] vs. /sitemap.xml etc. Isso resolve a discrepância inexplicada em /entries/:slug (+13 rpm) e mede a contribuição real do sitemap.
    Impacto: desbloqueia decisões seguintes · Esforço: baixo
  • P2
    Cache do resultado de collectSitemapUrls em Redis
    O sitemap é gerado on-demand a cada request, e cada request pode disparar de 5 a 2000 chamadas ao /entries (depende do tamanho das coleções). Já existe Cache-Control HTTP de 5min, mas as duas rotas (/sitemap.xml e /api/sitemap/[name]) reconstroem tudo separadamente. Cache in-process (Redis, TTL 5-10min) elimina reconstrução duplicada.
    Impacto: depende do tamanho das coleções · Esforço: baixo
  • P2
    Cache HTTP para /available-filters do cms-api
    Os filtros disponíveis por content type mudam quando entries são criados/editados, mas isso é infrequente durante uma sessão de navegação. Um Cache-Control com TTL curto (30-60s) permite CDN absorver a maior parte dos hits.
    Impacto: -9 a -13% adicionais no Bonsai · Esforço: baixo
  • P3
    Verificar short-circuit em HEAD e 404 do renderer
    Confirmar se essas rotas rodam getServerSideProps completo. Se sim, retornar mais cedo economiza fetches ao S3 e CMS. Não afeta o problema principal do OpenSearch de forma significativa, mas melhora latência e reduz custo de S3.
    Impacto: melhora tempo de I/O do renderer em ~5% · Esforço: baixo
  • P3
    Investigar itens fora do escopo
    Transação com error rate 100%, SSR mais lento de 5,8s, overhead de 108 ms por query no cliente OpenSearch. Cada um vale um card separado.

14. Conclusão

O que foi possível concluir com solidez

A causa principal do volume no OpenSearch foi identificada: cada request público do cms-api gera 2 queries no cluster, uma delas repetitiva e evitável. A busca em cms_content_types_v2 (o lookup de tipo de conteúdo) responde por quase metade do tráfego total do Bonsai e pode ser cortada com cache em memória — sem mudança arquitetural, sem risco relevante.

Essa conclusão vem de medição direta: o New Relic mostra que os dois índices consomem volumes praticamente iguais (534 vs 501 calls/min, ratio 1,07:1), o que só se explica se cada request gerar exatamente uma query em cada índice. É a assinatura clássica de N+1.

Ground truth: os dados do CloudWatch confirmam tudo

Rodar queries direto no log dos containers (log group /aws/ecs/mono-cms-prod-web) trouxe medição sem sampling e permitiu validar quase todos os números:

  • Total real em 24h: 755.391 requests (525 rpm) — bate com o New Relic (514 rpm), diferença de 2% dentro do ruído esperado.
  • Concentração massiva: Grupo Parvi (45,4%) + Grupo Automob (16,2%) = 61,6% dos requests, 75,7% do bandwidth. Top 10 contas = 85% de tudo.
  • Padrão temporal humano/comercial confirmado — vale às 03h-06h BRT (~13K/h), pico às 17h BRT (~50K/h). Bot dominante daria linha reta, o que não é o caso.
  • Bandwidth vem quase todo de entries? (99,6% dos 37,5 GB). Reforça que otimização de payload (per_page menor, _source_excludes) deve focar nesse endpoint.
  • Grupo Automob puxa responses de 119 KB médio (2,3× a média geral) — investigar content type específico dessa conta é ação de alto ROI.
O que ainda ficou como hipótese
  • Se o Grupo Parvi opera múltiplos sites (autoparvi, parvibyd, e possivelmente geelybrasil.com.br) — o accountId em si não separa isso. Precisa rodar a Query per siteId do Seção 4c para saber a distribuição.
  • Fan-out estrutural por site (média de blocos dinâmicos por página) — só será medido rodando a análise do JSON do S3. É a peça que fecha o "porquê" definitivo do ranking.
  • A discrepância de +13,4 rpm em /entries/:slug não foi resolvida. Único caller no código é [slug]/[item].tsx:157. Candidatos remanescentes: sampling do NR APM, retries HTTP, ou HEAD executando getServerSideProps.
  • Contribuição do sitemap ao CMS depende do tamanho das coleções em cada site — não medido.
Recomendação de próximos passos
  1. Implementar o cache do getContentTypeById — resolve praticamente metade do problema, funciona independentemente de qualquer outra ação e beneficia todas as contas proporcionalmente.
  2. Investigar por que Grupo Automob e Grupo Via 1 têm response média de 119 KB — puxam listas 3× maiores que a média (52 KB). Análise: qual content type usam, qual per_page, se há campos pesados sem _source_excludes.
  3. Rodar a análise de fan-out per site (queries da Seção 4c) — permite saber exatamente quantos sites cada conta opera e cruzar com pageviews reais. Fecha o "porquê" do ranking.
  4. Adicionar cache HTTP para /available-filters — endpoint muda pouco, é candidato natural a CDN cache. Reduz 10-11% do volume.
  5. Cachear collectSitemapUrls em Redis — elimina duplicação entre /sitemap.xml e /api/sitemap/[name].
  6. Investigar os pontos da seção 12 (error rate 100%, SSR de 5,8s, overhead de 108ms no OpenSearch, HEAD/404 pesados) como cards separados.
