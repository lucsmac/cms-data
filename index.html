Diagnóstico principal

93% do volume OS vem de 2 operações de search (cms_content_types_v2 + cms_content_entries_v3), geradas por 100% pelos 3 endpoints públicos chamados pelo renderer no SSR de sites publicados. O fan-out de 2,01 queries OS por HTTP request é a assinatura de N+1 no lookup getContentTypeById.

7. Quick win: cache in-memory de getContentTypeById

Impacto quantificado

Métrica Antes Depois Redução
Queries OS/min 1.035 ~501 -51,6%
Queries OS/dia 1,49M ~721K -769K/dia
Total Bonsai/dia 1,6M ~830K -48%
Índice content_types_v2 534 c/min ~0 -100%
Bônus: latência do próprio cms-api

New Relic mostra 110ms de avg por query em content_types_v2, enquanto o Bonsai reporta 2ms median / 6ms p95 no cluster. Isso significa ~108ms de overhead por query fora do cluster (rede, TLS, connection pool, serialização). Cache local elimina esse overhead 100% — impacto direto em latência do SSR do renderer e no Apdex de 71,69%.

8. Anomalias fora do escopo

Follow-ups para investigar
  • Highest error rate: 100% — algum endpoint falha 100% no período; descobrir qual
  • Slowest avg response: 5,8s — SSR trava em 5,8s no pior caso, provavelmente /entries/:slug com relações pesadas
  • Apdex 71,69% dissatisfying — reflexo do item anterior no experience real
  • msearch.create (1,31%) — o que é? Otimização legítima ou padrão a substituir?
  • Connection pool / keep-alive OS — 108ms de overhead sugere conexão não reusada; ver openSearchConfig.ts

9. Ações priorizadas

  • P1
    Cache in-memory de getContentTypeById
    TTL 5-10min + invalidação por mutação de ContentType/Field. Biblioteca: lru-cache (~20 linhas). Hit rate esperado >99% (content types são editados raríssimo).
    Impacto: -48% no Bonsai · Esforço: baixo
  • P2
    Cache HTTP + CDN para /available-filters
    Filtros mudam pouco; hit rate alto esperado.
    Impacto: -9 a -13% adicionais · Esforço: baixo
  • P2
    Cache-Control público em /entries + CDN
    TTL curto (30-60s) + CDN na frente absorve bots e re-visitas próximas.
    Impacto potencial: -20 a -30% adicionais · Esforço: baixo
  • P3
    Investigar anomalias fora do escopo
    Transação com 100% error rate, SSR lento de 5,8s, keep-alive do cliente OS.

10. Conclusão

O volume de 1,6M requests/dia ao Bonsai não é um mistério: é o resultado direto de ~740K pageviews de sites publicados, cada uma disparando 2 queries OS via getServerSideProps do renderer. Metade dessas queries é evitável trivialmente com cache in-memory do lookup de content type.

A spike de investigação está concluída. O caminho está claro para reduzir o Bonsai em quase metade com uma única mudança de baixo esforço.
